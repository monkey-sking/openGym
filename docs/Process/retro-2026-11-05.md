# 复盘回填：Build 67 交接清单（手机局域网视频直连、视频跳秒、训练前预置视频、手表持续同步与前台保持）

> 每修完一个用户报的问题必须填。门禁「复盘回填」检查项会比对本文与源码改动的先后。
> 四选一：防止（做不出这个错误）/ 拦截（做出来但被机器挡住）/ 暴露（漏到用户但被看见）/ 没挡住。
> 答「没挡住」必须新增一条机制——否则下次还会发生。

- **日期**: 2026-11-05
- **用户看到的现象**:
  1. 电脑端依赖 `local-server.mjs` / LaunchAgent 在 Mac 上跑 `8787` 中继服务，只装 Chrome 扩展无法直接和手机通过配对码连上。
  2. 手机点开始训练后，电脑端收到的 `videoUrl` 为 `null`，或打开视频后没有跳到链接 `?t=` 指定的起始秒数。
  3. 训练开始前无法在设置页预先配置计划和动作对应的视频，且默认计划和动作库缺少预置视频地址。
  4. 训练过程中手机和手表只在关键动作切换时同步，一旦丢包后没有持续同步；阶段结束后（尤其未开 Apple Health 写入时）手表容易退回表盘或后台；Watch 暂停页在 `start == 0` 时显示 `498298:09:55` 异常秒数。
  5. 手机设置页打开后显示「电脑不可达」，且配对时无法连上电脑扩展。
- **真实根因**:
  1. `frontend/ios/App/App/VideoSyncDiscoveryPlugin.swift:20-244` 原先只实现了 `NetServiceBrowser` 客户端发现，没有在 iPhone 本地启动 HTTP/SSE 服务；`tools/video-sync-extension/popup.js:52` 写死请求 `http://127.0.0.1:8787/pair/code`。
  2. `frontend/src/lib/video-sync.js:37-42` `videoSyncUrl()` 只读了 `entry.videoUrl` / `target.videoUrl` / `EXIDX[id].url`，未提取 `entry.note` / `target.note` 内嵌 URL，且 `videoSyncPos()` (`frontend/src/lib/video-sync.js:61-101`) 未解析 URL 中的 `?t=` / `&t=` / `#t=` 参数；同时 `tools/video-sync-extension/background.js:537-542` `commandFor(next)` 在 `start` 动作中只返回 `{ action: 'start', play: next.play }`，未透传 `pos` 与 `offset`。
  3. `frontend/src/lib/exercises.js` 内置动作库与 `frontend/src/lib/starter.js:46-47` 默认计划未挂载默认 `videoUrl`，`frontend/src/views/VideoSyncSettings.jsx` 缺少计划与动作级视频预配置面板。
  4. `frontend/src/lib/watch-sync.js:805-852` 仅在状态变化时发送最多 3 次重试快照，缺少训练期间周期心跳；`frontend/ios/App/Watch/WorkoutManager.swift:155` `guard enabled else { return }` 在未开健康写入时直接跳过 `HKWorkoutSession` 且无 `WKExtendedRuntimeSession` 兜底；`frontend/ios/App/WatchCore/Sources/WatchCore/SessionCore.swift:529-532` `pausedElapsed()` 只判了 `let start = w.start` 未判 `start > 0`。
  5. `PhoneRelayServer.swift:222` 将 `NWListener` 的初始等待状态 `.waiting` 误判为端口被占并执行了 `cancel()` 自杀逻辑，导致真机局域网服务器根本未成功监听；同时 `tools/video-sync-extension/background.js:210` 的 `isLocalRelay` 只判定了 127.0.0.1 未将局域网私有 IP（192.168.x / 10.x / 172.x）认定为免 Cookie 直连；并且 `VideoSyncSettings.jsx` 在未配对或旧电脑地址未通时错误将状态归为 `relay-unreachable` 吓唬用户。
- **为什么之前没发现**:
  1. 原有扩展测试（`background.test.mjs`、`local-server.test.mjs`）均以本机 `127.0.0.1:8787` 为前提，没有覆盖「手机做局域网服务器 + 扩展本地生成配对码并自动发现手机」以及「带 `?t=` URL 从手机 `start` 到浏览器 `<video>` 跳秒播放」的端到端链路。
  2. `watch-sync.test.js` 只测了单次状态变更触发的发送，未测训练进行中的周期保活；`SessionCoreTests.swift` 未覆盖 `start == 0` 时的 `pausedElapsed`。
  3. `NWListener` 在测试环境 mock 中直接置为 `.ready`，未模拟真实真机网络栈启动时必然触发的 `.waiting` 状态迁移。
  4. 仓库未接入 `delivery-gates` 门禁与红队机制。
- **被哪一层挡住**: 没挡住（问题 1–5 均由真机联调与交接清单暴露；`pausedElapsed` 在本次 Watch 模拟器截图自检中拦截）。
- **新增机制**:
  1. 接入 DSH `delivery-gates` 门禁（`.gate.conf.sh` + `Scripts/gate.sh` + `.githooks/pre-commit`），包含 6 项强制检查：`check_version`（全 Target 构建号一致且 >= 68）、`check_locales`（19 语言与源码 `t()` 零遗漏）、`check_extension_tests`（含 `discovery.test.mjs` 与 `e2e.test.mjs`）、`check_frontend_sync_tests`（含 `video-sync.test.js`、`watch-sync.test.js`、`VideoSyncSettings.test.jsx`）、`check_watchcore_tests`（含 `testPausedElapsedRequiresPositiveStartTimestamp`）、`check_retro_backfill`（改源码必写复盘回填）。
  2. 为全部 6 项检查配套编写 `REDTEAM_CASES` 故障注入红队用例，并用 `~/.dsh/skills/delivery-gates/redteam.sh /Users/runking/dev/openGym` 实测验证每条检查均能抓到注入标记并自动恢复。
  3. `PhoneRelayServer.swift` 正确处理 `.waiting` 瞬态，开启 `includePeerToPeer`；`background.js` 支持局域网 IP 免鉴权；未配对时状态收敛为「未配对」。
- **同类还有几处**:
  - 全局排查 `frontend/ios/App/Watch` 与 `WatchCore` 中所有讀取 `w.start` 计算时长的位置：`SessionStore.swift:262` 已判 `s > 0`，`SessionCore.swift:530` 已补齐 `start > 0`，其余位置均仅用于快照比较，无同类隐患。
  - 全局排查 `background.js` 与 `content.js` 中所有 `action` 分支（`start` / `resume` / `pause` / `sync` / `stop`）：确认 `start`、`resume`、`sync` 均已传递 `pos` 与 `offset`。

# 复盘回填（2026-11-06）：Build 70 修复真机 Wi-Fi 局域网监听与两端连接判定一致性

- **日期**: 2026-11-06
- **用户看到的现象**:
  1. 手机 openGym 上显示配对成功/连上了，但在电脑 Chrome 扩展弹窗中仍显示连不上（Looking for your phone / Failed to fetch）。
- **真实根因**:
  1. `frontend/ios/App/App/PhoneRelayServer.swift:185` 与 `235` 配置了 `parameters.includePeerToPeer = true`。在 iOS 16/17/18 上，该参数会将 `NWListener` 导向 Apple 点对点通道（AWDL/AirDrop 接口），导致普通 Wi-Fi 局域网（`en0`）路由器转发的 TCP 连接被 iOS 内核直接返回 Connection Refused。
  2. `PhoneRelayServer.swift:18` 中的 `phoneRelayBonjourType` 包含末尾点 `_opengym._tcp.`，而 `Info.plist` 中的 `NSBonjourServices` 为 `_opengym._tcp`，格式不匹配导致 Bonjour 权限校验异常。
  3. 手机端通过 `nativeFetch` 探测手机本地回环 `http://127.0.0.1:8787/health` 返回成功，在扩展尚未连入时手机前端直接显示「电脑可用」，导致用户误以为电脑已连入。
- **为什么之前没发现**:
  1. 模拟器环境没有物理 AWDL 接口与路由器硬件网段隔离，`includePeerToPeer` 在 Mac 模拟器下仍能被本机 localhost 访问，掩盖了真机跨设备 Wi-Fi 访问被拒绝的硬事实。
- **被哪一层挡住**: 没挡住（真机局域网网络探测与用户验收暴露）。
- **新增机制**:
  1. 移除 `PhoneRelayServer.swift` 中全部 `includePeerToPeer = true` 配置，恢复为标准基础设施 Wi-Fi TCP 监听。
  2. 修正 Bonjour 注册类型为 `_opengym._tcp`，与 `Info.plist` 严格一致。
  3. 构建号升级为 70，全 target 统一。
